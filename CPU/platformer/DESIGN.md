# DESIGN

Clean-room implementation of the platformer described in `SPEC.md` (v1.2,
errata E1-E16 from the two rounds of inspector answers included), written
from that document only. Freestanding C99 (`<stdint.h>`, `<stddef.h>`), no
floating point, no 64-bit types, all memory static.

## Files

| file | contents |
|---|---|
| `game.h` | public state (`GameState`), button bits, tile ids/classes, `game_reset`, `game_step`, test hook |
| `game.c` | all game logic, pure and deterministic (no I/O) |
| `levels.c` | own levels (2) and the six SPEC 9.1 test worlds |
| `tiles.c` / `tiles.h` | own 8x8 RGB332 art, generated by `tools/gen_tiles.py` from ASCII art |

| `test/run_vectors.c` | my host runner for the vectors (same output shape as the inspector's) |
| `test/scenarios.c` | host checks of blocks, items, enemies, shells, fireballs, climbing, spring, goal, water, death |
| `test/preview.c` | host render of chosen states through the real `platform.c` |

## Layers

`game.c` never touches hardware. `platform.c` only reads `GameState` and calls
`game_reset` once and `game_step` once per frame. The header exposes the
struct so a harness can read every field.

### `game_step` = SPEC section 1, in order

| spec step | code |
|---|---|
| 1 sample input | `map_buttons` (task bits -> spec pad word) |
| 2 freeze / frame timers / interval divider / frame counter | inline in `game_step` |
| 3 pseudo-random step | inline in `game_step` |
| 4 player routine | `player_routine` -> `player_control` (3.2 preprocess, 3.11 crouch, 3.6 jump, 3.3 params, movement step, 3.5, 7 scroll+clamp, 5.1 box, 4 tile collision, 3.15 pit) |
| 5 fireballs | `fireballs_step` |
| 6 object slots 0..5 | `objects_step`: spawn into empty slot, else `enemy_routine` (box, tiles, enemy-vs-enemy on odd frames, player-vs-enemy on even frames, movement unless frozen, despawn) or `item_routine` |
| 7 previous relative X, floating scores | inline + `popups_step` |
| 8 bouncing blocks (slot 1 then 0), tile write-back | `bounces_step` |
| 9 misc objects slot 3..0 | `misc_step` (jumping coins) |
| 10 level timer | `level_timer` |
| 11 previous A/B | inline |
| (own) life lost / level cleared | `handle_restart`, after step 11 |

### Numbers

All spec quantities keep their spec width and units (`Body` in `game.h`
documents every field). Signed reinterpretation of bytes goes through `s8()`
and 16-bit distances through `rel16()`, so nothing relies on
implementation-defined conversions; the arithmetic shift of the high nibble
in 2.2 is computed as `(v >> 4) - 16*sign` instead of shifting a negative
value. Hot structs are padded to 16 or 32 bytes (checked at compile time) so
slot indexing is a shift; the remaining `mul` instructions in the target
assembly run only on level load or once per frame outside loops.

## Conformance hook

The spec vectors need worlds and start states that `game_reset` alone cannot
produce, so `game.h` adds

```c
void game_reset_test(GameState *s, uint8_t world, uint16_t x, uint8_t y,
                     uint8_t pstate, uint8_t big);   /* world = W_FLAT..W_WATER */
```

It applies SPEC 9.2 (Gfall 40, camera 0, timers 0, face = mdir = right, ...)
in the named 9.1 world. Vector columns map to fields as follows:

| column | field |
|---|---|
| x, xs | `s->p.b.x`, `s->p.b.xs >> 4` |
| y, ys | `s->p.b.y`, `s->p.b.ys` |
| vx, vxf | `s->p.b.vx`, `s->p.b.vxf` |
| vy, vyf | `s->p.b.vy`, `s->p.b.vyf` |
| st | `s->p.pstate` |
| left | `s->cam` |

Input letters map to `game_step` bits: L 0x04, R 0x08, U 0x01, D 0x02,
A 0x10 (jump), B 0x20 (run).

## Rendering (`platform.c`)

* Half scale: a 16x16 level tile is one 8x8 art tile; logical (x, y) maps to
  screen `((x >> 1) - (camera >> 1), (y - 32) >> 1)`.
* Screen rows 0..7 are an opaque HUD bar (score, nuts, lives, timer). It is
  kept in a 1 KB RAM buffer and rebuilt only when a shown value changes, so
  per frame it costs a 256-word copy. Because the bar covers grid row 0, the
  playfield shown is grid rows 1..11.
* Background: aligned 32-bit stores only. The fine scroll offset splits into
  a word part and a byte part; each output word is a funnel shift of two
  source words. The loop runs tile column by tile column with the 8 lines
  unrolled, which keeps RV32E register pressure low.
* Sprites: 8x8 with a transparent key colour, per-sprite clipping, optional
  horizontal/vertical flip and one colour swap (fire robot, armored beetle).

### Measured cost (target build, `make emu`)

The full target binary runs in `tools/rv32emu`, which counts the
instructions between two `PRESENT` writes:

| input | frames | avg instr/frame | max instr/frame |
|---|---|---|---|
| scripted run-and-jump through level 1 (`tools/playthrough.txt`) | 2320 | 21.0k | 29.0k |
| random key mix (`tools/random_keys.txt`) | 6402 | 21.0k | 28.5k |
| level 3 walk (`tools/level3_run.txt`, build with `-DSTART_LEVEL=3`) | 1260 | 20.8k | 26.5k |
| random key mix from level 3 | 6402 | 19.9k | 28.6k |

Budget is about 41,000. The background is about 17k of that; game logic
averages 1-3k. A fire chain costs about 1k per frame (12 segment tests and
4x4 embers drawn without the general blitter). Level loads are included in
the maxima. Image size: 38.0 KB code (`.text`) + 8.3 KB read-only data
(art 6.6 KB, levels 1.1 KB) = 46.2 KB; RAM about 4.9 KB. I read the task's
"code under about 40 KB" as `.text`; if it means the whole image, the
quickest cut is packing sprites to 4 bits per pixel (about 1.6 KB) and
deriving the water tile set from the open-air set (about 1.7 KB).

### Hardware assumptions

* The framebuffer accepts aligned 32-bit stores, little-endian (lowest byte
  is the leftmost pixel). If it is byte-only, the background loops need byte
  stores (about 4x the store count).
* `PRESENT`, `VSYNC` and `KEYS_HELD` are read and written as 32-bit registers.
* The start-up code provides a stack and zeroed `.bss`; `main` never returns.

### Keys

`KEYS_HELD` has five keys, the game needs six buttons:

| key | buttons |
|---|---|
| bit 0 Up | Up and Run (run, fireball, climb up) |
| bit 1 Down | Down |
| bit 2 Left | Left |
| bit 3 Right | Right |
| bit 4 Space | Jump |

Up and B are both "non-A buttons" for the skid rule (3.8), so combining them
changes nothing there. The cost: running means holding Up, and a fire-powered
player throws a fireball on every Up press (except while climbing, where
throwing is blocked by 5.7).

## What is implemented

Everything in sections 1-4, 7 and the player-related parts of 5: frame order,
timers, PRNG, number formats, every movement rule (ground, air, skid, run
hold, jump classes, variable height, swimming, climbing, crouch, spring),
tile collision with all probe sets and classes, push-out, scrolling and
screen clamp, pit, grow / fire upgrade / injury / death sequences, block hits
(bump, break, multi-coin, hidden blocks, coin above a block, enemy knock from
below), coins and score codes, power-ups and invincibility, fireballs.

Objects implemented from section 6: spawning and despawning, the common
walker motion and ground/wall tests, stomp / kick / sliding-shell chains,
enemy-vs-enemy, defeat and knock rules, and these types: squat walker, shell
walker, ledge-aware shell walker, armored walker, hopper, spike walker and
spike egg, pipe plant, lava ball, slow and fast swimming fish, squid,
free-flying missile, short and long fire chain, the boss with its flames, and
all four items (growth, fire, invincibility, extra life). Hard mode A
(faster walkers, quicker revival, squat walkers replaced by armored ones) and
hard mode B (extra level entries, faster squid re-aim, shorter flame gaps)
are wired to the level loop.

**Not implemented**: glider, hoverer, thrower and its projectiles, cloud
rider (spike eggs are placed from the level list instead), leaping fish and
the frenzy, cannons (no cannon tile; the free-flying missile is there), all
platforms, the boss's projectiles in later stage groups and the floor
collapse, whirlpools (the flag exists, nothing sets it), the flag sequence,
pipe warps / bonus areas, vines growing out of blocks, brick debris.

### Level-object reference (`LevelEnemy {col, row, type, flags}`)

Entries are sorted by column. Ordinary enemies (walkers, hopper, spike
walker) give the row they stand on (Y = 16 row + 8). Other objects use
Y = 16 row, interpreted per type:

| type | col, row | flags | slots | sprite slots |
|---|---|---|---|---|
| `E_SPIKE` | row stood on | `LE_EGG`: drops as a spike egg from Y = 16 row + 8 | 1 | `SPR_CALTROP_A/B`, `_EGG` |
| `E_PLANT` | left pipe column, pipe top row | | 1 | `SPR_CLAW_A/B`, `SPR_CLAW_ROD` |
| `E_LAVA` | column; row sets the leap height (peak about 16 row + 50..95) | | 1 | `SPR_SLAG` |
| `E_FISH`, `E_FISH_FAST` | position (Y = 16 row) | | 1 | `SPR_DRONE_A/B` |
| `E_SQUID` | position | | 1 | `SPR_JELLY_A/B` |
| `E_MISSILE` | position; row 11 hits a standing player, row 10 passes over | | 1 | `SPR_DART` |
| `E_CHAIN`, `E_CHAIN_LONG` | the pivot block (put a solid tile there) | `LE_CCW`: other spin | 1 / 2 | `SPR_EMBER` (middle 4x4) |
| `E_BOSS` | row stood on (32 px tall, 32 wide) | | 2 | `SPR_BOSS_A_*`, `SPR_BOSS_B_BL/BR`, `SPR_JET_A/B_L/R` |

## Changes for SPEC v1.1 and v1.2 (inspector answers)

| erratum | what changed in the code |
|---|---|
| E1 | `LEVEL_END` is a wall for the side probes and a head bump; only the feet end the level |
| E2 | interval divider starts at 0 and is never reloaded by a level start; level start clears all frame and interval timers |
| E3 | `Player.abproc` holds the A/B bits as processed by 3.2 (after the water-bottom clearing); step 11 copies it to `prevab`, so frames without an input step (grow, fire upgrade, first injury frames, the 200 frame, death) keep the last control frame's bits. Fireballs use the processed bits too |
| E4 | springs follow the new 5.8: 13 frames run in the object pass (`spring_object`), +2 px on frames 1-8, -2 px on 9-13, A edge on 5-13 selects -12, the ground step keeps running without the position update, and the scroll logic receives the animation step number 1..4 as `moved` |
| E5 | no wall test on any landing frame or on the ledge-turn frame |
| E6 | each object slot holds one pending score (`GameState.sc[6]`, 48-frame timer); points or the life are added at 43; a new score in the same slot replaces the old one; codes capped at 11; coin pickups stay immediate |
| E7 | enemy-vs-enemy runs in the higher slot's routine against slots i-1..0, the "acted" bit lives on the lower slot and is cleared when the pair is tested without overlap; squat walker knocked from below ends 4 px higher with `Vy` = -3, 100 points once |
| E8 | on screen for collisions = `X - camera` in -7..255, `Yh` = 1, `Y` <= 224; box edges are clipped to 0..255 before the overlap test |
| E9 | injury: control on 239..201, the 200 frame ends the sequence without a movement step |
| E10 | a hopper treats a BUMPED tile as ordinary ground (lands and rebounds), it is not knocked |
| E11 | `face`/`mdir` may hold 3; a fireball thrown with `face` = 3 goes right (own choice, as allowed) |
| E12 | item emergence: 1 px on every frame with frame counter AND 3 = 0 (not paused by the freeze), 17 rises to 25 px above the block, then it starts moving; drawn, collidable and despawn-checked only after 5 px |
| E13 (corrects E6) | pending scores advance in the object pass right after each slot's routine (`score_advance`), paying when the value before the count-down is 43: 5 frames after a score set in the slot's own turn, 6 after one set into a slot whose turn has passed |
| E14 (corrects E7) | every object stores its on-screen flag and box position (`Enemy.boxx`, `boxy`) at the start of its own routine; the enemy-vs-enemy test uses the stored values for both enemies, and the player-vs-enemy test uses them too |
| E15 | the spring is a level object (`E_SPRING`, entry at column 112) and its logic runs in its slot's turn; it does nothing while the freeze counter is non-zero, so the animation pauses while the ground step still treats it as animating |
| E16 | the invincibility item uses the hopper's landing rule only: a bumped block under it is ground, it is not knocked |
| harness | `test/run_vectors.c` splits each row on `|` before parsing, so a button field written without a space before `|` can no longer shift a script |

## Verification done

* `make test`: 38/38 spec vectors pass, plus 46/46 scenario checks (items,
  stomps, kicks, shell chains, fireballs, climbing, the 13-frame spring,
  goal, water, death, injury, pit, hard mode, E3 previous-A/B handling,
  E13 score payment frame, E7 squat knock, E10/E16 hopper rule on a bumped
  block, E12 emergence phase and height, E15 spring in its slot and paused by
  the freeze, 30k frames of random play). The inspector reports 3000/3000
  hidden scripts on the v1.0 and v1.1 builds; E12-E16 concern objects only,
  which the player-only test worlds do not contain.
* A deliberately wrong constant (walk cap 23) makes 8 vectors fail, so the
  runner is not vacuous.
* Vectors and scenarios run clean under gcc's AddressSanitizer and
  UndefinedBehaviorSanitizer.
* Target build: `make` produces the four `.s` files with zero warnings
  (`-std=c99 -Wall -Wextra -pedantic` on top of the required flags); no
  `memset`/`memcpy` calls are emitted from game code, but `platform.c`
  defines both in case a compiler does.
* No spec constant was changed to make a test pass.

## Own choices

Values and behaviour the spec leaves open. Spec constants are separate (they
live in the tables at the top of each section of `game.c` with section
references). Items that SPEC v1.1 and v1.2 now settle were removed from this list.

### Logic

1. Grid is 13 x 256 tiles. Columns past 255 repeat column 255, so the
   SPEC 9.1 worlds are unbounded to the right (confirmed in the answers, Q3).
   Game levels are at most 256 columns and the camera stops at the level's
   right end (`cam_max`); in test worlds the camera has no limit.
2. Screen clamp (7) compares `X - camera` as a signed 16-bit distance. The
   answers (Q1) confirm the result: anything just left of the camera is
   clamped to the camera.
3. Yh values 0x80..0xFF count as "above the screen", not as a pit.
4. The death jingle (3.15) is silent and lasts 150 frames.
5. Losing a life: lives - 1, power back to small, level restarts from its
   start. Game over (last life) resets the whole game with 3 lives. In test
   worlds life loss does nothing (the player keeps falling, Q4).
6. Size sequences: power changes at contact, the size flips at 248 (grow) or
   240 (injury).
7. Spring: the scroll logic receives `((n - 1) >> 2) + 1` as `moved`, where
   n is the spring counter the player step sees (frame 1, the landing frame,
   is an ordinary movement frame; then 1 on frames 2-4, 2 on 5-8, 3 on 9-12,
   4 on frame 13, as confirmed). Fallback: if the player lands on a spring
   tile while no spring object is in a slot (for example all slots were busy
   when its entry came due), the spring logic runs once after slot 5.
8. Pipes have no warps: the down-pipe check does nothing and the side-pipe
   tile impedes like a wall.
9. `LEVEL_END` touched by the feet while falling starts an own 90-frame
   level-clear pause, then a time bonus of 50 points per timer unit and the
   next level. After the last level the game loops to level 1 with hard
   mode A on, and after the second loop also hard mode B.
10. Level timer: 300 units, one unit per 24 frames, the player dies at 0.
    Disabled (0) in test worlds.
11. No pause key, so the paused path of section 1 is never taken.
12. Brick-break points (50) are added immediately, like coins.
13. Fireballs: thrown only while the player is in control; the bounce keeps
    `Vyf`; an explosion lasts 8 frames and keeps the slot busy; `face` = 3
    throws to the right.
14. Wall test direction comes from the sign of `Vx`; it is skipped when
    `Vx` = 0.
15. "Turn to face the player" keeps `|Vx|` (walk speed if it was 0).
16. Items: the invincibility item gives 1000 points; a growth or extra-life
    item knocked by a bumped block gets `Vy` = -3, flags S and A, speed +-16
    away from the player.
17. Four jumping-coin slots. A coin above a bumped block becomes a jumping
    coin positioned from that coin's own tile.
18. Two bounce slots used alternately; if the slot is still busy, its bounce
    finishes at once (final tile written). At most two brick removals per
    frame.
19. Multi-coin brick: the hit after its timer ran out still gives a coin,
    then the brick becomes a used block.
20. Level object entries give the grid row of the tile the enemy stands on,
    so the spawn Y = 16 * row + 8 puts it on that tile. A flag marks entries
    that exist only in hard mode B.

### Presentation

21. Half-scale view, HUD bar over grid row 0, 128 x 96 window following the
    spec camera (`camera >> 1`). Drawing treats `face` = 3 as facing right.
22. Injured player blinks: drawn on even frames only (as 5.3 says); the
    invincible player's body colour cycles with the frame counter.
23. Jumping-coin popups last 40 frames; pending scores are drawn while their
    48-frame timer runs. Both rise 1 px every 2 frames.
24. All art, palette and both level layouts are my own: a maintenance robot,
    hex-nut coins, bolt crates, a fuzz mite and beetles, cables, exhaust
    stacks, a charging-pad goal. Level 1's opening (columns 10-60) was
    redesigned from scratch after the inspector's note: a walled pen, a
    walkway with an inset crate and an end stop, a pit with one stepping
    stone, and a crawlspace only the small robot fits through.
    The section 6 objects got their own designs too: a boiler golem (boss)
    with a monitor eye, furnace grille and treads, firing plasma jets; slag
    drops (lava ball); pipe claws on piston rods (plant); drone pods
    (fish); cable jellies (squid); rivet darts (missile); caltrop bots and
    their spiked seeds (spike walker / egg); ember chains (fire chain).
    Level 3 "Boiler Works" and the extra fish and squid in level 2 are my
    own layouts.

### Own choices for the section 6 objects

25. Two-slot objects (boss, long chain) spawn only into a slot whose upper
    neighbour is free and below slot 4; otherwise the entry waits.
26. Pipe plant: entry column = left column of a two-column pipe; the plant
    is centred on it (X + 8) and its low position is 24 px below 16 row,
    which puts its head exactly at the pipe's top. Drawing clips it there.
    The 33 px proximity test uses the player's X against the plant's X.
27. Pipe plants take part in enemy-vs-enemy only to be defeated by a sliding
    shell (6.4 says shells kill them; 6.3 excludes plants from the contact
    test). They never turn anything. See QUESTIONS.md Q2.
28. Lava ball: "placed at `Yh = 2`" read with Y = its spawn Y (16 row). It
    relaunches only after it has fallen back below the screen and its timer
    is 0. Pseudo-random bytes: R1 for `Vyf`, R2 for the timer.
29. Invincible player (star): the boss and lava balls are neither defeated
    nor harmful; everything else follows 5.2 step 2.
30. Fireballs explode on the fireproof targets (armored walker, missile, lava
    ball) without effect, as they already did on the armored walker.
31. Squid: in the sinking phase after the 2-tick timer it sinks at the same
    1 px per 2 frames. Re-aim uses R3. Fish bob direction at spawn uses R1.
32. Fire chain: pivot segment's top-left = (X + 4, Y + 36), the centre of
    the block at (col, row). The spin pauses during the freeze. The player
    contact also needs the player in normal control and `Yh = 1`.
33. Boss: approach timer kept at 32 while the player is at least 32 px right
    of the boss, counting down otherwise; chasing while it runs and the
    player is to the right. Range re-picked (R2) at each reversal; jump timer
    reloaded (R5) on landing at its spawn floor. Flame gaps use my order
    191, 64, 64, 191, 191, 64, 191, 64, starting with 191 at spawn.
34. Boss flame: own box B12 (2, 4)-(30, 12) for its 32 x 16 drawing,
    1 px/f straight, drifting 1 px every 2 frames toward the boss floor
    + 4, 12 or 20 (R4), hurting on odd frames like a thrown projectile but
    not reversed. Defeated boss falls with gravity 15, terminal 2.
